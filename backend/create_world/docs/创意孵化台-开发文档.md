## 1. 项目定位与边界

### 1.1 一句话定义

**创意社区 + AI 落地分析师**：用户发布创意，平台自动产出「创意度 / 可行性 / 落地链路 / 技术栈与能力清单」结构化分析报告；同时所有用户都能对创意打分、评论、收藏，形成「AI 参考分 + 社区大众分」两套并行评分体系。

### 1.2 明确不做（防止范围失控）

| 不做 | 原因 |
| --- | --- |
| 比赛评委后台（多轮评审、评委分配、评分表模板） | 定位是社区，不是赛事系统 |
| 复杂审批流（工作流引擎） | 单人项目，内容治理用「下架 / 标记」即可 |
| 实时协作编辑 | 无需求，成本高 |
| 私信 / IM | 与创意主题无关 |
| AI 生成创意（自动投稿） | 会让社区数据失真，且生成内容监管成本高 |
| 多租户 | 单体社区，无租户概念 |

### 1.3 三个必须先定死的核心概念

1. **两套分数不混合展示**：AI 分在前端必须带「AI 参考」标识，社区分带「大众综合」标识，榜单也分榜，不允许合成一个「总评分」，否则产品叙事会退化成"AI 打分网站"。
2. **AI 分析是异步资产**：报告一旦生成即落库版本化，前端只读；重新分析必须显式触发并保留历史版本（`ai_analysis_report.version`），避免"分数天天变"。
3. **社区分一人一票**：`(idea_id, user_id)` 唯一，允许改分（覆盖更新），不允许重复计票。

### 2.2 四条工程决策（本设计据此展开）

**D0｜版本基线：Spring Boot 3.5.16（已实测确认，不是设计偏好）**

原 pom 为 Boot 4.1.2：`mvn compile` 通过，但 `spring-boot:run` 启动失败：

```
Failed to process import candidates for configuration class
[com.alibaba.cloud.ai.autoconfigure.dashscope.DashScopeAgentAutoConfiguration]:
Type org.springframework.boot.autoconfigure.web.client.RestClientAutoConfiguration not present
```

原因：`spring-ai-alibaba-starter-dashscope:1.1.2.0` 内的 `DashScopeAgentAutoConfiguration` 用 `@AutoConfigureAfter` 引用了 Boot 3 的包路径，Boot 4 重构了该类位置，第三方 starter 未跟进。

处置：回退 parent 至 `3.5.16`，同步改回 Boot 3 的 starter 命名（`webmvc→web`、`spring-boot-starter-kafka→spring-kafka`、四个 `*-test→spring-boot-starter-test`、`mybatis-plus-spring-boot4-starter→mybatis-plus-spring-boot3-starter`）。

实测结果：编译通过、启动 5.5s、Flyway 自动建 17 张表、`vector 0.8.7` 扩展可用。

**结论：不要为"用新版本"而升 Boot 4，Spring AI Alibaba 生态基线仍是 3.5。**

**D1｜数据访问层选 MyBatis-Plus，不用 JPA**
理由：报告、任务、榜单都是 JSONB + 自定义 SQL（向量 `<=>` 排序、`ON CONFLICT` 幂等插入）为主，MyBatis-Plus 写 SQL 更直接；JPA 对 pgvector 自定义类型与 JSONB 的映射是额外负担。

**D2｜向量检索只用 pgvector，ES 降级为可选**
理由：
- 创意主数据在 PostgreSQL，向量与业务同库可在**一个事务内**写入创意 + 切片，避免"ES 写成功、库写失败"的双写不一致；
- pgvector 的 HNSW 索引在万级~百万级切片量下足够，本项目规模（预估 < 10 万创意）远未到 ES 的适用区间；
- 双写两套检索系统是单人项目的典型烂尾来源。

结论：ES 依赖可先保留不启用（或用 `spring.autoconfigure.exclude` 关闭自动配置），若后续需要中文全文检索再加，**不作为阶段 1~3 的前置条件**。

**D3｜同步用 WebMVC，Redis 用同步客户端（已落实）**
已把 `spring-boot-starter-data-redis-reactive` 换成 `spring-boot-starter-data-redis`。SSE 用 `SseEmitter`（Servlet 栈原生支持），不需要 WebFlux。

```
    ├── redis
    ├── kafka
```

分层规则（强约束，Code Review 卡点）：

- Controller 不写业务，只做参数转换 + 权限校验 + 调 Service；
- `ai` 包不依赖 `web`/`community`，只依赖 `infra` + `common`，保证可单测；
- 所有跨模块调用走 Service 接口，不直接注入别的模块的 Mapper。

### 3.3 关键时序

**S1｜创意发布 + 查重 + 触发分析**

```
Client            IdeaService        SearchService      Kafka        AnalysisConsumer
  │ POST /ideas/publish │                  │              │               │
  ├────────────────────>│                  │              │               │
  │                     │ 1. 校验状态/权限  │              │               │
  │                     │ 2. 落库(status=1) │              │               │
  │                     ├─3. embed(标题+方案)──────────────> DashScope      │
  │                     ├─4. 召回 TopK 相似 ─>│              │               │
  │<──5. {ideaId, similar[]} ─┤              │              │               │
  │                     ├─6. 写 idea_chunk + 相似关系        │               │
  │                     ├─7. 创建 task(mode=LIGHT) ─────────>│               │
  │  GET /ideas/{id}/analysis/stream (SSE)     │              │               │
  ├────────────────────────────────────────────┼─────────────>│ 8. RUNNING    │
  │<──────── stage 事件 / 增量文本 / 最终报告 ────┼──────────────┤ 9. 落 report  │
```

**S2｜深度分析（Kafka 异步）**

```
Client  POST /ideas/{id}/analysis/deep
   │           │
   │      创建 task(mode=DEEP, status=PENDING)
   │      投递 idea.analysis.deep(topic)
   │<── {taskId}
   │      GET /analysis/tasks/{taskId} 轮询（progress / stage / errorMsg）
```

**S3｜社区打分**

```
POST /ideas/{id}/scores {score, shortComment}
  → 限流检查（user + ip）
  → 唯一键 upsert(idea_id, user_id)
  → 计算用户权重 weight
  → 异步刷新 Redis ZSET 榜单（延迟双删/定时补偿）
  → 返回最新社区分（贝叶斯聚合值）
```


## 5. 数据库设计

### 5.1 扩展与基础约定

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- 约定：
-- 主键 BIGINT（雪花），前端一律按 string 传输
-- 时间列统一 TIMESTAMPTZ
-- 逻辑删除用 deleted SMALLINT DEFAULT 0（MyBatis-Plus @TableLogic）
-- 金额无；分数用 NUMERIC(4,2)
```

### 5.2 建表 SQL

#### 5.2.1 用户

```sql
CREATE TABLE sys_user (
    id              BIGINT PRIMARY KEY,
    username        VARCHAR(64)  NOT NULL,
    nickname        VARCHAR(64)  NOT NULL,
    password_hash   VARCHAR(100) NOT NULL,
    avatar_url      VARCHAR(512),
    bio             VARCHAR(256),
    role            VARCHAR(16)  NOT NULL DEFAULT 'USER',  -- USER / ADMIN
    trust_weight    NUMERIC(3,2) NOT NULL DEFAULT 1.00,   -- 打分权重 0.00~1.00
    risk_flag       SMALLINT     NOT NULL DEFAULT 0,      -- 0 正常 1 观察 2 冻结
    points          INTEGER      NOT NULL DEFAULT 0,
    deleted         SMALLINT     NOT NULL DEFAULT 0,
    created_time    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_time    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uk_user_username ON sys_user (username) WHERE deleted = 0;
```

#### 5.2.2 分类与标签

```sql
CREATE TABLE idea_category (
    id           BIGINT PRIMARY KEY,
    name         VARCHAR(32) NOT NULL,
    code         VARCHAR(32) NOT NULL,
    sort         INTEGER     NOT NULL DEFAULT 0,
    enabled      SMALLINT    NOT NULL DEFAULT 1,
    created_time TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uk_category_code ON idea_category (code);

CREATE TABLE idea_tag (
    id            BIGINT PRIMARY KEY,
    name          VARCHAR(32) NOT NULL,
    use_count     INTEGER     NOT NULL DEFAULT 0,
    created_time  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uk_tag_name ON idea_tag (name);

CREATE TABLE idea_tag_rel (
    idea_id BIGINT NOT NULL,
    tag_id  BIGINT NOT NULL,
    PRIMARY KEY (idea_id, tag_id)
);
CREATE INDEX idx_tag_rel_tag ON idea_tag_rel (tag_id);
```

#### 5.2.3 创意主表

```sql
CREATE TABLE idea (
    id                  BIGINT PRIMARY KEY,
    title               VARCHAR(120) NOT NULL,
    cover_url           VARCHAR(512),
    category_id         BIGINT       NOT NULL,
    author_id           BIGINT       NOT NULL,
    status              SMALLINT     NOT NULL DEFAULT 0,   -- 0草稿 1已发布 2归档 3下架
    summary             VARCHAR(500),                     -- 一句话概述
    background          TEXT,                             -- 创意背景
    goal                TEXT,                             -- 目标
    plan_text           TEXT,                             -- 初步方案（正文）
    expect_effect       TEXT,                             -- 预期效果
    est_cost            VARCHAR(64),                      -- 预估成本（如 "1-5万"）
    est_duration        VARCHAR(64),                      -- 预估周期
    view_count          BIGINT       NOT NULL DEFAULT 0,
    favorite_count      BIGINT       NOT NULL DEFAULT 0,
    comment_count       BIGINT       NOT NULL DEFAULT 0,
    score_count         INTEGER      NOT NULL DEFAULT 0,  -- 社区打分人数
    score_sum           NUMERIC(12,2) NOT NULL DEFAULT 0, -- 社区原始分总和
    score_avg           NUMERIC(4,2),                     -- 算术均值（展示用）
    score_bayes         NUMERIC(4,2),                     -- 贝叶斯分（榜单用）
    ai_score_total      NUMERIC(4,2),                     -- AI 综合参考分
    ai_creativity_score NUMERIC(4,2),                     -- AI 创意度
    ai_feasibility_score NUMERIC(4,2),                    -- AI 可行性折算分
    ai_report_id        BIGINT,                           -- 当前生效报告
    latest_task_id      BIGINT,
    publish_time        TIMESTAMPTZ,
    deleted             SMALLINT     NOT NULL DEFAULT 0,
    created_time        TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_time        TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX idx_idea_author      ON idea (author_id, status);
CREATE INDEX idx_idea_category    ON idea (category_id, status, publish_time DESC);
CREATE INDEX idx_idea_ai_score    ON idea (ai_score_total DESC)     WHERE status = 1 AND deleted = 0;
CREATE INDEX idx_idea_bayes       ON idea (score_bayes DESC)        WHERE status = 1 AND deleted = 0;
CREATE INDEX idx_idea_publish     ON idea (publish_time DESC)       WHERE status = 1 AND deleted = 0;
CREATE INDEX idx_idea_title_trgm  ON idea USING gin (title gin_trgm_ops);
```

> 冗余字段（分数计数、均值）是刻意的：榜单与列表页高频读，避免每次 `AVG()` 聚合。更新时用 `UPDATE ... SET score_count = score_count + 1, score_sum = score_sum + ?` 保证并发安全。

#### 5.2.4 向量切片

```sql
CREATE TABLE idea_chunk (
    id           BIGINT PRIMARY KEY,
    idea_id      BIGINT       NOT NULL,
    chunk_index  SMALLINT     NOT NULL,      -- 切片序号，0 起始
    chunk_type   VARCHAR(16)  NOT NULL,      -- TITLE / SUMMARY / PLAN / AI_REPORT
    content      TEXT         NOT NULL,
    token_count  INTEGER      NOT NULL DEFAULT 0,
    embedding    vector(1024) NOT NULL,      -- 维度与所选 embedding 模型一致
    created_time TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_chunk_idea ON idea_chunk (idea_id);
CREATE INDEX idx_chunk_vec  ON idea_chunk USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
```

> 维度说明：DashScope `text-embedding-v3` 支持 1024/768/512，默认 1024。**改维度必须重建索引并全量重算**，因此维度写入配置并在启动时校验。若后期换模型，新增 `idea_chunk_v2` 表并行跑，不要原地改列。

## 6. API 设计

### 6.1 通用约定

**统一响应**

```json
{ "code": 0, "msg": "ok", "data": {} }
```

分页：`{ "list": [], "total": 0, "pageNo": 1, "pageSize": 10 }`

**ID 传输**：所有 `BIGINT` 主键在 JSON 中输出为**字符串**（雪花 ID 超出 JS 安全整数范围）；前端禁止 `Number()` 转换；请求参数 id 也一律传字符串。

**认证**：`Authorization: Bearer <jwt>`；未登录可读（广场/详情/榜单），写操作 401。

**频率限制**：写接口默认 30 次/分钟/用户；打分接口 10 次/分钟/用户；超限返回 `code=42901`。

**错误码表**

| code | 含义 |
| --- | --- |
| 0 | 成功 |
| 40001 | 参数错误 |
| 40101 | 未登录 / token 失效 |
| 40301 | 无权限 |
| 40401 | 资源不存在 |
| 40901 | 状态冲突（如草稿已发布仍想编辑） |
| 42901 | 请求过于频繁 |
| 50001 | 服务内部错误 |
| 51001 | AI 调用失败（可重试） |
| 51002 | AI 输出解析失败 |
| 51003 | 分析任务仍在执行 |
| 52001 | 打分异常（风控拦截） |

## 7. AI 分析引擎

### 7.1 分析链路

```
┌───────────────────────────────────────────────────────┐
│ 1. 预处理                                              │
│    文本清洗 → 长度归一（超长截断/摘要）→ 分片(检索用)     │
├───────────────────────────────────────────────────────┤
│ 2. 查重（确定性，先于 LLM）                             │
│    embedding(标题+summary+plan前512字) → TopK 召回       │
│    maxSimilarity ≥ 阈值 → riskLevel 高，附带参考创意      │
├───────────────────────────────────────────────────────┤
│ 3. Agent 分析（Spring AI ChatClient + Tool 池）         │
│    system(角色+评分锚点+输出契约) + user(创意全文+查重上下文)│
│    → 工具按需调用（查重/参考案例/技术选型知识）           │
│    → 强制 JSON 结构化输出                                │
├───────────────────────────────────────────────────────┤
│ 4. 后处理                                              │
│    JSON 解析（容错）→ 分数裁剪到 [0,10] → 权重加权 →      │
│    一致性校验（分数与理由矛盾时打标）→ 落库 + 更新 idea 冗余字段│
└───────────────────────────────────────────────────────┘
```

**关键原则：LLM 只负责"生成理由与结构化内容"，分数由可复现的规则收口。**
即：LLM 输出 `creativityScore` 后，后端做 clamp + 与相似度联动修正（撞车严重时创意度上限压到 6 分），最终 `totalScore = w1*creativity + w2*feasibility`，权重来自 `ai_scoring_config`，不由模型算。

### 7.2 工具池（Agent Tools）

用 Spring AI 的 `@Tool` 注解在进程内注册（`ChatClient.prompt().tools(...)`）。**不建议一开始就拆成独立 MCP Server**：进程内工具调试成本低、事务简单；等工具需要跨服务复用（如给其他项目用）再抽 MCP，届时工具签名不变，替换成本很低。

| 工具 | 签名 | 职责 | 是否调外部 |
| --- | --- | --- | --- |
| `vectorDedupTool` | `(title, summary, plan) -> DedupResult` | 向量召回相似创意，返回 TopK + 最大相似度 + 撞车风险等级 | PG + Embedding |
| `similarCaseTool` | `(ideaId, topK) -> List<CaseBrief>` | 取相似创意的 AI 报告要点，作为"参考别人怎么落地"的素材 | DB |
| `techStackTool` | `(domain, keywords, constraints) -> TechSuggestion` | 基于本地知识库（技术选型清单表/文档）给出候选技术栈，避免模型瞎编 | 本地知识库（PG 表 + 向量检索） |
| `costEstimateTool` | `(scale, stack, duration) -> CostBand` | 成本区间估算（规则表，不由模型自由发挥） | 规则表 |
| `roadmapTool` | `(plan, level) -> RoadmapDraft` | 生成阶段化路线骨架（模板 + LLM 填充） | 模板 |
| `metricTool` | `(text) -> TextStat` | 字数/完备度检查（背景/目标/方案是否齐全） | 无 |

**约束**：工具必须是**纯查询/幂等**的，禁止在工具内写库改状态（避免模型一次调用产生副作用）。所有写库动作在 Agent 返回后的后处理阶段统一执行。

### 7.3 结构化输出契约

后端定义 `AnalysisReportDTO`，Prompt 中直接给出 JSON Schema（比"请输出 JSON"稳定得多），并用 Spring AI 的 `BeanOutputConverter` 或 `responseFormat=JSON`。


1. 严格 `ObjectMapper` 解析成功 → `1`

3. 仍失败 → 任务 `FAILED`，`error_code=51002`，保留 `raw_response` 供排查

### 7.4 Prompt 设计

**Prompt 文件化管理**：放在 `src/main/resources/prompts/`，命名 `analysis-light-{version}.md`、`analysis-deep-{version}.md`。启动时加载，版本号写入报告，**改 Prompt 必须升版本**（这是控制分数漂移的唯一可追溯手段）。

**System Prompt 骨架**

```
你是资深产品技术顾问，负责评估一个创意方案的"新颖度"与"可落地性"。
评分锚点（必须严格对齐，不要给中庸分）：
- 创意度 9~10：领域内未见同类，且解法有结构性创新
- 创意度 7~8：思路新颖，与已有方案差异明显
- 创意度 5~6：常见思路的组合优化
- 创意度 3~4：已有成熟方案的轻度改写
- 创意度 0~2：直接复制现有产品
- 可行性 8~10：技术路径成熟，单人/小团队 1 个月内可验证
- 可行性 5~7：路径清晰但存在 1~2 个明确卡点
- 可行性 0~4：核心依赖不成立（缺数据/缺硬件/合规禁止/成本不可承受）

硬性要求：
1. 不得编造具体产品、论文、数据；不确定时在 reason 中说明"不确定"。
2. 相似度上下文由工具提供，若 maxSimilarity ≥ 0.85，创意度不得高于 6。
3. 只输出 JSON，不要 markdown 代码块，不要解释。
```

**User Prompt 骨架**

```
【创意标题】{title}
【一句话概述】{summary}
【分类】{categoryName}    【标签】{tags}
【背景】{background}
【目标】{goal}
【初步方案】{planText}
【预期效果】{expectEffect}
【预估成本/周期】{cost} / {duration}

【查重上下文】
maxSimilarity={maxSimilarity}
相似创意：{similarCases 简报，含各自 AI 报告要点}

【任务】输出 JSON：
{schema}
```

**校准（关键，别省）**

- 准备 20~30 条标杆样本（`ai_calibration_sample`），人工标定创意度/可行性/等级；
- 每次改 Prompt 或权重后跑 `/admin/calibration/run`，输出：
  - 平均绝对误差 MAE（创意度、可行性分别统计）
  - 等级判断准确率
  - 各分数段样本的偏差方向（是否系统性偏高/偏低）
- 验收门槛建议：创意度 MAE ≤ 1.0，可行性 MAE ≤ 1.0，等级准确率 ≥ 70%。达不到就调 Prompt 锚点，不要靠改权重掩盖。

### 7.5 轻量 vs 深度

| 维度 | LIGHT | DEEP |
| --- | --- | --- |
| 触发 | 发布时自动 / 用户手动 | 用户显式请求 |
| 执行 | 线程池（`analysis-light-*`，核心 4 线程）+ SSE 推送 | Kafka `idea.analysis.deep`，独立消费者组 |
| 输入 | 标题 + summary + plan 前 1500 字 | 全文 + 相似创意报告 + 技术知识库检索 |
| 工具 | 仅 `vectorDedupTool` | 全部工具 |
| 模型 | `qwen-turbo` 类小模型 | `qwen-plus` / `qwen-max` |
| 耗时预期 | 3~8s | 30~90s |
| 落库 | 报告 `version` 自动 +1 | 同左，但 `is_active` 切换后旧版置 0 |

**幂等与并发**：同一 idea 同时只允许一个 RUNNING 任务（Redis 锁 `analysis:lock:{ideaId}`，TTL 5 分钟）；重复请求直接返回现有 taskId（`error_code=51003` 场景用于"稍后再试"提示）。

**积分/配额**：深度分析每用户每天 5 次（可配置），超限返回 42901；管理员不限。轻量分析不限额但受并发锁约束。

### 7.6 分数漂移与成本控制

漂移控制四件套：

1. `temperature=0.3`（可配置，默认不高于 0.5）；
2. 高分/低分锚点写死在 system prompt，禁止"中庸倾向"；
3. 分数与理由一致性校验：若 `feasibilityLevel=HIGH` 但 `feasibilityScore<6`，判为矛盾，`parse_status=2` 并在后台列表打标；
4. 每次报告记录 `model_name + prompt_version + config_version`，出现线上质疑时可复现。

成本控制：

| 手段 | 说明 |
| --- | --- |
| Embedding 缓存 | `sha256(文本) → 向量` 存 Redis 7 天，重复查重不重复计费 |
| 报告缓存 | 同一 idea 内容哈希未变时，重新分析走"内容未变，复用报告"提示，不重复调模型 |
| 长文本截断 | plan 超 6000 字先做分段摘要再进主 Prompt |
| 批量 Embedding | 切片入库用 batch 接口（一次 25 条上限内） |
| 降级 | 模型超时/限流 → 重试 1 次 → 退化为"仅查重 + 规则评分"，报告标 `parse_status=2` 并提示"AI 参考分不可用" |

## 8. 社区机制与榜单

### 8.1 打分规则

- 范围 `0.00 ~ 10.00`，允许一位小数（`0.5` 步长），后端校验；
- `(idea_id, user_id)` 唯一，重复提交视为**修改**（覆盖 `score`，`updated_time` 刷新，`score_count` 不变）；
- 作者不能给自己的创意打分（返回 40301）；
- 提交后 `idea.score_sum / score_count` 通过原子 UPDATE 更新，`score_avg = score_sum / score_count`；
- 短评（`short_comment`，≤140 字）与正文评论分离：短评只展示在「评分明细」区，不进评论区，避免垃圾评论污染。

**聚合算法（展示分）**

```
剔除极值（n ≥ 8 时生效）：去掉最高 1 个、最低 1 个
score_avg = 剩余分数按 weight 加权平均
```

`weight` 取用户 `trust_weight` 快照（写入 `community_score.weight`），便于事后重算。

### 8.2 榜单算法

**A. 社区人气榜（贝叶斯平均，解决"1 个 10 分碾压 100 个 7 分"）**

```
score_bayes = (C * m + Σ(score_i * weight_i)) / (C + Σ weight_i)
其中 C = 10（先验票数），m = 7.0（全站均值，每日重算）
```

上榜门槛：`score_count >= 5` 且 `status = 1`。

**B. 热度榜（Reddit hot 变体）**

```
hot = log10(max(view_count, 1)) + 0.5 * log10(score_count + 1) + 0.3 * log10(favorite_count + 1)
      - (now - publish_time) / 48h
```

`/ 48h` 为时间衰减因子，让新创意有机会冒头。

**C. AI 创意度榜**

直接按 `idea.ai_creativity_score DESC`，但必须带**社区校验门槛**：`score_count >= 3` 才上榜。否则会出现"AI 高分但没人看"的孤儿内容占据榜首，观感极差。

**D. 新星榜**：`publish_time` 在 7 天内，按 `hot` 排序。

**实现方式**：
- 榜单 Top 50 走 Redis ZSET 缓存（key：`rank:popular`、`rank:creativity`、`rank:feasibility`、`rank:rising`），TTL 10 分钟；
- 定时任务（每小时）全量重算贝叶斯分并写回 `idea.score_bayes`，同时刷新 ZSET；
- 打分/收藏/浏览不实时改榜单，靠 10 分钟 TTL 自然过期，避免高频写 Redis；
- 读接口若缓存未命中，直接走 SQL `ORDER BY ... LIMIT 50` 兜底并回填。

### 8.3 防刷风控

分层策略（全部在 `community` 模块的 `ScoreRiskService` 内实现）：

| 层级 | 规则 | 处置 |
| --- | --- | --- |
| L1 前置 | Redis 令牌桶：用户 10 次/分钟、IP 20 次/10 分钟 | 42901 拦截 |
| L2 身份 | 注册 < 24h 的用户 → `weight = 0.3` | 计入但不影响榜单 |
| L3 行为 | 用户对同一作者连续打分 > 5 条，且分数方差 < 0.5 | `risk_flag=1`，`weight=0.5`，写 `risk_event` |
| L4 分布 | 用户 24h 内打分中 ≥ 80% 落在 [0,2] 或 [8,10] | `weight=0.3`，写 `risk_event` |
| L5 关联 | 同 IP 多账号对同一创意打分 | 只计 1 票，其余 `weight=0` |
| L6 复核 | 管理员在后台看到 `risk_event` 列表，可重置/冻结 | `risk_flag=2` 后所有打分不进聚合 |

原则：**不做静默删分**，只调权重并在后台留痕（`risk_event`），可解释、可回滚。

### 8.4 评论

- 一级评论按时间倒序 + 热度（赞数）可选排序；
- 二级回复按时间正序（对话可读性）；
- 评论数 `idea.comment_count` 只统计 `status=0` 的评论；
- 删除为软删（`status=2`），前端显示「该评论已删除」占位，保留楼层结构；
- 内容过滤：敏感词表（本地文件 + 可选第三方审核 API），命中则 `status=1` 待人工复核。

## 9. 检索与查重

### 9.1 切片策略

| 切片类型 | 来源 | 处理 |
| --- | --- | --- |
| `TITLE` | 标题 + 一句话概述 | 直接作为一条 |
| `SUMMARY` | 背景 + 目标 | 拼接，≤ 512 token |
| `PLAN` | 初步方案 | 按段落聚合到 ~512 token，重叠 50 token |
| `AI_REPORT` | 报告的核心结论（创意度理由 + 可行性理由 + 落地路线摘要） | 分析完成后追加，用于"找相似落地路径" |

单创意切片数上限 20，超出只保留前 20（按 PLAN 优先）。

**入库时机**：草稿不切片（省成本）；`publish` 时切片 + 向量化；报告生成后追加 `AI_REPORT` 切片。

### 9.2 相似度检索

```sql
SELECT c.idea_id,
       1 - (c.embedding <=> #{queryVector}) AS similarity
FROM idea_chunk c
JOIN idea i ON i.id = c.idea_id
WHERE i.status = 1 AND i.deleted = 0
  AND i.author_id <> #{excludeAuthorId}      -- 查重时排除自己
ORDER BY c.embedding <=> #{queryVector}
LIMIT #{topK};
```

- 距离算子用 `<=>`（cosine），与 HNSW `vector_cosine_ops` 对齐；
- MyBatis 传向量：自定义 `VectorTypeHandler`，把 `float[]` 序列化为 `'[0.1,0.2,...]'::vector`；
- 相似度阈值：**撞车警告 0.85**、**参考推荐 0.75**（可配），`maxSimilarity < 0.75` 视为"未撞车"。

### 9.3 混合检索

```
① 向量召回 Top 50（语义）
② 关键词召回 Top 50（title/plan ILIKE 或 trgm 相似）
③ 标签/分类过滤（硬过滤，作用于两路召回之后）
④ RRF 融合：score = Σ 1 / (k + rank_i)，k = 60
⑤ 截断 Top N 返回，附带相似度与命中原因（vector / keyword / both）
```

阶段 1 可先只做 ①（向量）+ 分类过滤，关键词用 `ILIKE` 兜底；阶段 3 再上 RRF 与 trgm。

### 9.4 创意聚类（可选加分项）

离线任务（每周）：对所有已发布创意的 `SUMMARY` 向量做 KMeans（k=6~8）或对相似度图做连通分量，人工给簇打标签：「高潜力」「脑洞难落地」「成熟可原型化」「红海赛道」。

落地方式：`idea.cluster_id` 字段 + `idea_cluster` 表（id / label / desc / size）。前端广场提供「按聚类浏览」。此项**排到阶段 4**，不阻塞主链路。

### 10.3 关键交互设计

**A. 发布页的查重提示**

编辑正文 `debounce 1500ms` 调 `POST /ideas/check-similar`（传标题 + 前 800 字），返回后：
- `maxSimilarity ≥ 0.85`：顶部 `a-alert type="warning"`，列出 Top3 相似创意（可点击新窗口打开）；
- `0.75 ≤ maxSimilarity < 0.85`：`a-alert type="info"`「发现相关创意，建议参考其落地路径」；
- 低于阈值不提示。

不阻塞发布（否则用户会为了绕过提示而改写措辞），但要记录用户是否看了提示。

**B. 详情页分析报告**

- 分析未完成：骨架屏 + 进度条（轮询 `GET /analysis/tasks/{taskId}` 2s 一次，或 SSE）；
- 已完成：分区块卡片（创意度 / 可行性 / 落地路线 / 技术栈 / 建议），每块可折叠；
- 分数用 `a-progress` 圆环 + 文案标签，**必须带「AI 参考」角标**与 `tooltip`「由大模型生成，仅供参照」；
- Mermaid：`mermaid.render()` 渲染 `roadmap_mermaid`；渲染前做安全处理（禁用 `click` 指令、`securityLevel: 'strict'`），渲染失败降级为文本树。

**C. 打分器**

- 10 分滑条（步长 0.5）+ 短评输入 + 提交；
- 已打分则回显并显示「修改我的评分」；
- 未登录点击 → 弹登录框；
- 提交成功后本地更新分布条形图（乐观更新，失败回滚）。

**D. 双分数展示规范**

```ts
  { label: '轻量', value: 1 },
  { label: '深度', value: 2 },
];
```

注册到 `DICT_TYPE`：`IDEA_STATUS`、`ANALYSIS_TASK_STATUS`、`FEASIBILITY_LEVEL`、`ANALYSIS_MODE`、`IDEA_CATEGORY`（后端字典表维护，前端只管渲染）。

### 10.5 SSE 客户端实现要点

不用原生 `EventSource`（无法带 Authorization header）。改用：

```ts
const resp = await fetch(url, {
  headers: { Authorization: `Bearer ${token}`, Accept: 'text/event-stream' },
  signal: abortController.signal,
});
const reader = resp.body!.getReader();
// 按 \n\n 分帧，解析 event / data
```

要点：组件卸载必须 `abort()`；断线重连最多 2 次（指数退避）；重连后先查任务状态再决定是否继续拉流（避免重复渲染）。

### 10.6 图表（阶段 3）

ECharts 封装成两个通用组件：
- `ScoreDistributionChart`：分数桶柱状图（详情页 + 后台）
- `TrendChart`：创意发布/打分趋势折线（后台看板）

技术方向分布用横向条形图（标签 top 10）。

## 11. 权限模型

| 角色 | 能力 |
| --- | --- |
| 游客 | 浏览广场/详情/榜单/搜索、查看报告公开部分 |
| 普通用户 USER | 上述 + 发布/编辑自己的创意、发起分析、打分、评论、收藏、关注 |
| 管理员 ADMIN | 上述 + 分类/标签/权重/校准集管理、内容下架、用户权重调整、任务与风控监控 |

实现：

- Spring Security + JWT，`@PreAuthorize("hasRole('ADMIN')")` 保护 `/admin/**`；
- 数据级校验在 Service 内做（作者校验、状态校验），不靠前端隐藏按钮；
- 前端权限走后端菜单/按钮权限（Vben `auth` 指令），permission code 约定：`createworld:idea:publish`、`createworld:admin:scoring` 等。

**不做**：复杂 RBAC（角色-菜单-数据权限三维）。单管理员场景，两个角色足够。

## 13. 可观测性与运维

**日志**
- 统一 `traceId`（`MDC`，从 `X-Request-Id` 或生成）；
- AI 调用日志必打：`taskId / model / promptVersion / tokenIn / tokenOut / costMs / 是否降级`；
- **禁止打印完整 Prompt 与用户正文**（隐私 + 日志膨胀），只打长度与哈希。

**指标**（后续接 Micrometer + Prometheus，阶段 4）
- `ai_analysis_duration_seconds`（按 mode 分）
- `ai_analysis_fail_total`（按 error_code）
- `ai_token_cost_total`（按 model）
- `community_score_reject_total`（按 rule_code）
- `analysis_task_queue_size`

**健康检查**：`/actuator/health`（PG / Redis / Kafka / MinIO 探活，AI 用轻量探活但不进 health 主判定，避免模型抖动导致服务被判死）。

**部署**：`docker-compose.yml` 起 PG(+pgvector) / Redis / Kafka / MinIO / app；数据库用 Flyway 管理迁移（`V1__init.sql`、`V2__index.sql`），禁止手工改库。

**备份**：PG 每日 `pg_dump`；向量可重算，不必单独备份（重建成本 = 全量 embedding 费用，需评估）。

## 14. 分阶段计划与验收标准

单人开发，按**能演示**切分，每个阶段结束都能跑通一条完整链路。

- [ ] PG 装 pgvector，写入 1 条向量并做一次近邻查询
- [ ] MyBatis-Plus 在 Boot 4.x 下可用（或确认需降级到 3.x）
- **出口条件**：上述 4 项全部通过，否则调整版本基线并更新本文档

### 阶段 1｜创意库底盘（1.5 周）

- [ ] 用户注册/登录/JWT
- [ ] 创意 CRUD + 草稿 + 发布 + 标签 + 分类
- [ ] 切片 + Embedding 入库
- [ ] 发布时查重（返回相似列表）
- [ ] 广场列表（分类/排序/分页）+ 详情页
- [ ] 前端：创作页、广场、详情页（报告区先占位）
- **验收**：注册 → 写创意 → 发布 → 看到「发现 2 条相似创意」→ 广场能搜到 → 详情能打开；一条创意在 `idea_chunk` 有 ≥1 条向量且近邻查询返回结果正确

- [ ] 前端：报告卡片、落地路线 Mermaid、进度轮询
- **验收**：发布 1 条真实创意，30s 内拿到结构化报告，字段完整率 100%；跑校准，创意度 MAE ≤ 1.0；故意让模型返回非法 JSON，能正确降级且任务标记失败

### 阶段 3｜社区互动（1.5 周）

- [ ] 社区打分（唯一、改分、分布统计）
- [ ] 风控 L1~L5 + `risk_event` 留痕
- [ ] 评论 + 二级回复 + 点赞

- **验收**：同一用户对同一创意只能 1 票（重复提交变修改）；刷 20 条 10 分会被限流/降权；榜单 Top50 与 SQL 直算结果一致
